## 🟥 Сценарий 1 — Сервер недоступен (Server Down)

**Алерты:** `CohubServerDown` (`up{job="cohub"} == 0`, for 1m) · резервный `CohubErrorStorm` (`error_rate > 50%`, for 2m). **Severity: critical.**

| Поле | Значение |
|---|---|
| **Симптом** | Пользователи получают 5xx / страница не открывается. Grafana-панель «Сервер (up)» = **DOWN** (красная). |
| **Где видно** | Prometheus → Alerts → `CohubServerDown` (firing); Alertmanager → `#alerts-critical`; Grafana панель `up{job="cohub"}`. |
| **Влияние** | Полный отказ: недоступны логин, комнаты, расходы, платежи. Высший приоритет. |

### 🔍 Диагностика (по шагам)
1. **Подтвердить, что лежит именно приложение, а не мониторинг.** Открыть `GET /health/` напрямую.
   - Отвечает **200** → приложение живо, проблема в сети/скрейпе Prometheus (см. шаг 5).
   - Не отвечает / 5xx / таймаут → приложение действительно лежит, идём дальше.
2. **Проверить процесс/контейнер веба.** Render: Dashboard → Service → Events/Logs. Локально/VM:
   ```bash
   # Жив ли процесс gunicorn/runserver?
   ps aux | grep -E "gunicorn|runserver"
   # Последние ошибки приложения
   tail -n 100 logs/errors.json | jq .
   ```
3. **Проверить зависимости.** `/health/` проверяет БД и кеш — если приложение поднимется, тело ответа покажет, что именно `error`:
   ```bash
   curl -s http://<host>/health/ | jq .
   # {"status":"unhealthy","database":"error: ...","cache":"ok"}
   ```
   - `database: error` → недоступна БД (PostgreSQL на проде): проверить `DATABASE_URL`, статус инстанса БД, лимит подключений.
   - `cache: error` → недоступен кеш-бэкенд.
4. **Память/CPU (OOM-kill).** Render → Metrics или панель Saturation: всплеск RAM перед падением = вероятный OOM. 
5. **Если `/health/` = 200, а Prometheus всё равно DOWN:** причина в скрейпе, не в сервисе:
   - `host.docker.internal` отсутствует в `DJANGO_ALLOWED_HOSTS` → Django отдаёт `400 DisallowedHost` (см. троблшутинг в MONITORING_NOTION.md).
   - На проде: неверный `target`/`scheme: https` в `prometheus.yml`.

### 🛠️ Митигация / устранение
- **Краш приложения:** перезапустить сервис (Render → Manual Deploy → Restart; локально — перезапустить gunicorn). Это первичная мера для восстановления доступности.
- **БД недоступна:** восстановить инстанс БД / увеличить лимит подключений; при необходимости — failover на реплику.
- **OOM:** временно увеличить план инстанса (RAM) или число воркеров уменьшить; найти источник утечки после стабилизации.
- **Плохой деплой (см. ниже Откат).**

### ↩️ Откат (rollback)
Если падение началось **сразу после деплоя** — откатиться на предыдущий рабочий релиз:
```bash
# Render: Dashboard → Deploys → выбрать предыдущий успешный → "Rollback"
# Git-driven деплой:
git revert <bad_commit> && git push     # безопасно, без переписывания истории
```
Подтвердить в `git log`, что откат соответствует последнему «зелёному» CI (см. `.github/workflows/ci.yml`).

### ✅ Подтверждение восстановления
1. `GET /health/` → **200**, тело `status: healthy`.
2. Prometheus → Targets: `cohub` снова **UP**; алерт `CohubServerDown` ушёл в **resolved**.
3. Grafana: панель «Сервер (up)» зелёная, трафик восстановился, error rate < 1%.

### 📟 Эскалация
`critical` → page on-call немедленно → +5 мин team lead → +15 мин eng. manager (см. Escalation Policy в [ALERT_RULES.md](ALERT_RULES.md)).

### 📝 Пост-мортем
Завести запись: время начала/конца, MTTR, корневая причина (5 why), что починили, какой алерт сработал (и вовремя ли), action items (например, добавить readiness-probe, лимиты памяти, тест на конфиг).

## 🟧 Сценарий 2 — Повышенный процент ошибок (High Error Rate)

**Алерт:** `CohubHighErrorRate` (`5% < error_rate ≤ 50%`, for 5m). **Severity: warning** (перерастает в critical `CohubErrorStorm` при > 50%).

| Поле | Значение |
|---|---|
| **Симптом** | Часть запросов падает (5xx/4xx). Пользователи видят ошибки на отдельных действиях. |
| **Где видно** | Grafana панель «② Errors — error rate» (жёлтая/красная); метрика `cohub_error_rate_percent`; Alertmanager. |
| **Влияние** | Частичная деградация: страдает часть функций (например, только платежи или только создание комнат). |

### 🔍 Диагностика
1. **Понять масштаб.** Сводка: `GET /api/metrics/summary/` → блок `alerts` (`high_error_rate`, `service_down`). Если `service_down: true` (>50%) — переключиться на **Сценарий 1**.
2. **Локализовать источник по логам.** В `logs/errors.json` уже лежат только записи уровня ERROR (5xx) с `path`, `status_code`, `request_id`:
   ```bash
   # Топ эндпоинтов по числу ошибок за последнее время
   tail -n 500 logs/errors.json | jq -r '.path' | sort | uniq -c | sort -rn | head
   # Конкретные 5xx
   tail -n 200 logs/errors.json | jq 'select(.status_code>=500) | {path,status_code,request_id,message}'
   ```
3. **Один эндпоинт или весь сервис?**
   - Все ошибки на одном `path` → баг/регрессия в конкретной вьюхе или её зависимости (внешнее API, миграция БД).
   - Разрозненные `path` → общая причина: БД, кеш, внешний провайдер (например, PayPal), исчерпание пула соединений.
4. **Платежи?** Если ошибки в `/payments/` или метрика `cohub_payment_success_rate` падает — смотреть `logs/payments.json` (`event_type: payment_error`) и доступность PayPal.
5. **Связь с деплоем.** Сопоставить старт роста ошибок с временем последнего деплоя (`git log`, Render Events).

### 🛠️ Митигация
- **Регрессия после деплоя** → откат (см. блок ниже).
- **Внешний провайдер (PayPal) лёг** → включить деградацию: показать пользователю понятную ошибку, не терять заказ (заказ остаётся `pending`, вебхук/повтор подтянет позже). Платёжная логика уже изолирована и не валит остальной сервис.
- **Исчерпание ресурса БД** (too many connections) → перезапуск воркеров / увеличение лимита; проверить долгие запросы.
- **Битые данные/миграция** → применить недостающую миграцию или хотфикс.

### ↩️ Откат
Как в Сценарии 1: Render Rollback или `git revert <bad_commit> && git push`. Откат — самый быстрый способ вернуть error rate в норму, если причина — свежий релиз.

### ✅ Подтверждение восстановления
- `cohub_error_rate_percent` < 5% (а в идеале < 1%), панель Errors снова зелёная.
- В `logs/errors.json` новые 5xx по проблемному `path` прекратились.
- Алерт `CohubHighErrorRate` → resolved.

### 📟 Эскалация
warning → Slack `#devops-alerts`; если за 1 час не локализовано или error rate растёт к 50% → поднять до critical и звать backend team lead.

### 📝 Пост-мортем
Записать: какой эндпоинт, корневая причина, почему не поймал CI/тесты, нужен ли новый тест/алерт на этот класс ошибок.

## 🟨 Сценарий 3 — Высокая задержка ответов (High Latency)

**Алерты:** `CohubHighLatency` (`p95 > 5000ms`, for 3m, warning) · ранний `CohubElevatedLatency` (`2000 < p95 ≤ 5000`, for 5m, info).

| Поле | Значение |
|---|---|
| **Симптом** | Приложение «тормозит»: страницы и API отвечают медленно, но без ошибок (статусы 2xx). |
| **Где видно** | Grafana панель «③ Latency — p95 / avg»; метрики `cohub_p95_latency_ms`, `cohub_avg_latency_ms`. |
| **Влияние** | Деградация UX; под нагрузкой может перерасти в таймауты и ошибки (Сценарий 2). |

### 🔍 Диагностика
1. **Подтвердить и оценить тренд.** Grafana панель Latency: p95 пробил 2s (info) или 5s (warning)? Растёт линейно или скачком?
2. **Проверить насыщение (Saturation).** Панель «④ Saturation — CPU/RAM»:
   - CPU > 80% или RAM > 85% (алерты `CohubHighCPU`/`CohubHighMemory`) → ресурсный потолок: нужен скейл.
   - Ресурсы в норме, но латентность высокая → узкое место в БД/внешнем вызове, не в CPU.
3. **Скоррелировать с трафиком.** Панель Traffic (`rate(cohub_requests_total[1m])`): всплеск нагрузки → естественный рост латентности (см. результат нагрузочного теста как базовую линию: p95 ≈ 640ms при 100 юзерах).
4. **Найти медленные эндпоинты по логам.** В `logs/requests.json` есть `latency_ms` по каждому запросу:
   ```bash
   # Самые медленные запросы за последнее время
   tail -n 1000 logs/requests.json | jq -r '[.latency_ms, .path] | @tsv' | sort -rn | head -20
   # Средняя латентность по эндпоинту
   tail -n 1000 logs/requests.json | jq -r '.path' | sort | uniq -c | sort -rn | head
   ```
5. **БД.** Медленные/неиндексированные запросы — частая причина. Проверить, применены ли индексы (миграция `0013_..._idx_...`), нет ли N+1.

### 🛠️ Митигация
- **Нехватка ресурсов** → горизонтальный/вертикальный скейл (больше воркеров gunicorn / план инстанса на Render).
  > ⚠️ **Важно про метрики при скейле.** Счётчики метрик живут в памяти процесса (синглтон `MetricsCollector`). Прод сейчас запускает gunicorn с **1 воркером**, поэтому метрики корректны. Если увеличиваете число воркеров/инстансов — Prometheus будет скрейпить лишь один из них и видеть несогласованные счётчики. Перед скейлом переведите метрики на `prometheus_client` в multiprocess-режиме (или общий стор) и настройте скрейп всех инстансов.
- **Медленный эндпоинт из-за БД** → проверить/добавить индекс, устранить N+1, включить/прогреть кеш (часть ответов уже кешируется, напр. `/api/metrics/` через `cache_page`).
- **Тяжёлая синхронная операция** → вынести в фоновую очередь (в проекте есть воркер `run_worker` и планировщик `scheduler`).
- **Медленный внешний вызов (PayPal)** → проверить таймауты, не блокировать основной поток.

### ↩️ Откат
Если рост латентности совпал с деплоем (например, добавили тяжёлый запрос) — откатить релиз (Render Rollback / `git revert`).

### ✅ Подтверждение восстановления
- `cohub_p95_latency_ms` вернулась под порог (< 2000ms — норма), панель Latency зелёная.
- CPU/RAM в норме; алерты latency → resolved.
- Выборочная проверка медленного ранее эндпоинта в `logs/requests.json` показывает `latency_ms` в норме.

### 📟 Эскалация
info → наблюдаем; warning (p95 > 5s) → Slack `#devops-alerts`; если деградация ведёт к ошибкам/таймаутам → поднять severity и подключить backend.

### 📝 Пост-мортем
Записать: что стало узким местом (БД/CPU/внешний вызов), какой фикс применён (индекс/кеш/скейл/очередь), обновить базовую линию латентности (бенчмарк через Locust).

## ➕ Бонус-сценарий — Падение успешности платежей (Payment Failures)

Не входит в обязательные 3, но критичен для монетизации. **Алерт:** `CohubPaymentFailureRateHigh` (`payment_success_rate < 90% и payments_total > 0`, for 5m, critical).
- **Диагностика:** `logs/payments.json` → `jq 'select(.event_type=="payment_error" or .status=="failed")'`; доступность PayPal; режим (`sandbox`/`live`) и валидность ключей.
- **Митигация:** проверить ключи/вебхук PayPal; неоплаченные заказы остаются `pending` и доберутся вебхуком/повтором — деньги не теряются.
- **Подтверждение:** `cohub_payment_success_rate` > 99%, новые `payment_confirmed` идут.

## 🔁 Как тренировать плейбук (Game Day)

Чтобы плейбук был «живым», периодически прогоняйте учения:
1. **Server down:** остановить приложение → убедиться, что `CohubServerDown` сработал и пришёл в `#alerts-critical`.
2. **High latency / saturation:** запустить Locust (`loadtest/run_loadtest.ps1`) с большим числом юзеров → наблюдать рост p95 и срабатывание latency-алертов.
3. **High error rate:** временно «сломать» эндпоинт (например, кинуть исключение) → убедиться, что 5xx попадают в `logs/errors.json` и `CohubHighErrorRate` срабатывает.

> После каждого учения обновляйте этот документ: пороги, шаги, контакты.
