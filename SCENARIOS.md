# 🧩 COHUB · Ответы на 4 сценария

Разбор четырёх ситуаций про операционную готовность. Стек: метрики `cohub_*`,
логи `logs/*.json`, `/health/` и `/api/metrics/*`. Что делать при аварии — `PLAYBOOK.md`.

## 1️⃣ Locust: p95 80мс при 10 юзерах → 2400мс при 50. Какие 4 слоя проверять?

Сначала — **против чего гоняли тест**: раннеры бьют в `localhost:8000`, а это либо
`runserver` + **SQLite**, либо docker `--workers 3` + Postgres. От этого зависит слой №1.

Скачок ×30 при нагрузке ×5 = **встали в очередь**, а не «просто медленнее».
Считаем: ~48 запросов в очереди × ~50мс ≈ 2400мс. Ищем, что ограничивает параллелизм.

По убыванию вероятности:

1. **База данных.** Чаще всего она — потолок. SQLite вообще **блокирует запись** (create
   room / add expense выстраиваются в очередь). У Postgres — пул соединений, N+1, нет индексов.
   *Признак:* тормозят страницы с данными и записью, а не health/статика.
2. **Слоты обработки (воркеры/потоки).** Их меньше, чем параллельных юзеров → очередь.
   *Признак:* медленно **равномерно по всем путям** (одно ядро может быть в потолке, а CPU по хосту — нет).
3. **Внешние вызовы в запросе.** Дашборд ходит в PostHog за флагом, платежи — в PayPal.
   Блокирующий вызов занимает слот. *Признак:* медленно только на этих страницах.
4. **Ресурсы хоста (CPU/RAM).** Панель Saturation. Обычно последний: очередь наступает раньше, чем CPU в потолке.

Быстрая развилка по логам:
```bash
tail -n 1000 logs/requests.json | jq -r '[.latency_ms,.path]|@tsv' | sort -rn | head
```

## 2️⃣ 2 ночи. Алерт: error rate 45%. Вы на сервере. Какие команды?

Порядок: **масштаб → класс ошибок → где → остановить кровь.** Причину — утром.

```bash
# Масштаб: 45% или уже >50%?
curl -s http://localhost:8000/api/metrics/summary/ | jq '.alerts'

# Живы ли база и кеш?
curl -s http://localhost:8000/health/ | jq .
#   {"status":"error","checks":{"database":"error","cache":"ok"}}

# Это 5xx (наш баг) или 4xx (throttle/авторизация)?
tail -n 500 logs/requests.json | jq -r '.status' | sort | uniq -c | sort -rn | head

# Диск не забит?
df -h

# Где именно 5xx
tail -n 500 logs/errors.json | jq -r '.path' | sort | uniq -c | sort -rn | head

# Совпало с релизом?
git log --oneline -10
```

**Развилка:** ошибки на одном пути → баг в этой странице; на разных → общая причина (база, кеш, PayPal).

**Остановить кровь (быстрее всего):**
- Сломалось после релиза → откат. **Render → Deploys → Rollback** быстрее, чем `git revert` (тот пересобирает билд).
- Подвисли воркеры / пул базы → **рестарт** (Render → Manual Deploy → Restart).

Проверить: error rate < 5%, новых 5xx нет, алерт погас. Утром — разбор.

## 3️⃣ Request rate упал до нуля, хотя сервер `up`. Причина? Чем отличается от high error rate?

Ноль запросов при живом `up` и `/health/` = 200 значит: **Prometheus сайт достаёт, а
пользователи — нет** (или запросы не считаются). Причины по вероятности:

1. **Трафик не доходит.** Сломано выше приложения: балансировщик / DNS / роутинг Render.
   `up=1` доказывает только «Prometheus → сайт», а не «пользователь → сайт».
2. **Метрика не пишется.** Сломался/отключился `MetricsMiddleware`. (Один рестарт нуля не
   даёт — `rate()` переживает сброс счётчика; ноль = инкрементов реально нет.)
3. **Реально нет трафика.** Ночь, низкая нагрузка.

**Проверка за 30 секунд:** зайти самому → тикает `cohub_requests_total`?
Тикает → был провал трафика (proxy/DNS). Не тикает → проблема в метрике.

**Отличие от high error rate:**

| | Request rate = 0 | High error rate |
|---|---|---|
| Запросы доходят? | Нет | Да |
| Проблема в | доступности (выше сайта) или метрике | качестве ответов (5xx/4xx) |
| Аналогия | никто не заходит в магазин | магазин полон, всем дают брак |

`up` = «удался ли скрейп `/metrics`» — это про эндпоинт метрик, а не про реальных пользователей.

## 4️⃣ Чеклист: 6 пунктов с ❌. До Demo Day 2 недели. Как приоритизировать?

**Демо ≠ прод.** Это короткое, малонагруженное событие. Значит масштаб и высокую
доступность можно **отложить**, а наверх идут три вещи: happy-path работает на сцене,
данные не утекают и не теряются, есть быстрый откат если сломается вживую.

**Приоритет по риску, а не по лёгкости.** Три корзины:

- **P0 — чинить обязательно.** Теряет/светит данные, ломает платежи, дыра в безопасности
  (`DEBUG=True`, нет HTTPS, утёкший секрет), «нельзя задеплоить/откатиться».
- **P1 — пережить демо.** Работают мониторинг и алерты (видеть сбой вживую), `/health/`,
  бэкап с проверенным восстановлением, отрепетированный откат.
- **P2 — режем.** Лишние панели, доки, косметика, нагрузка/масштаб.

**Правила при дедлайне:**
- Сначала все P0.
- **Глубина против ширины:** лучше полностью закрыть 3–4 пункта, чем наполовину 6.
- P2 вычёркиваем **осознанно** и записываем как известный пробел.
- Сначала проверь, что каждый ❌ **реальный**, а не отставание доков (у нас алерты были
  помечены «заглушка», а Telegram реально работал — не трать на это 2 недели).

> Операционная готовность — не самое яркое, но именно она отделяет тех, кто переживает запуск. 🔧
